# Shared T4 lifecycle helper

`bash bench/aws/t4.sh` coordinates one existing single-T4 instance from one host.
Supported types are `g4dn.xlarge`, `g4dn.2xlarge` and `g4dn.4xlarge`.
Lifecycle control and detached remote jobs share exact acquisition tokens.
The original source and its later `wait_stopped` patch were recovered from local
transcript tool inputs and inspected as text, not executed. Private environment
files, paths, instance discovery, provisioning and guest installation are not
carried over.

## Configuration

Use the same `G16_AWS_REGION`, `G16_AWS_ACCOUNT`, `G16_AWS_OWNER`,
`G16_AWS_STOP_ROLE_ARN`, `G16_AWS_SCHEDULER_GROUP` and normal AWS CLI credential
configuration as the other runners. Defaults are `us-east-1`, `123456789012`,
`bench-runner` and Scheduler group `default`; the role has no default.
`AWS_PROFILE` selects the CLI profile. No IAM creation or policy changes are made.

Also set:

- `G16_T4_INSTANCE`: exact existing instance ID, no tag-based fallback or creation.
- `G16_T4_STOP_SCHEDULE`: exact independently armed Scheduler schedule name.
- `G16_T4_STATE_DIR`: optional local state directory, default
  `$HOME/.cache/snarkrs/t4`. All participating lanes must share this directory on
  the same host. Do not delete or replace it while a lease or operation exists.
  Use a separate directory for each account/region/instance tuple.

The coordinator must finish the cross-build before renting GPU time. Use the
mandatory native `aws_instance` arm/start/use lifecycle separately, with an
independent verified deadline before start. The helper cannot arm, start, launch,
terminate, extend or cancel a deadline. Do not use the old scratch helper or the
safe runner's launch path to bypass native lifecycle authorization.

## Commands

- `acquire <lane>`: require a running T4 with matching ID, Owner and normal IAM
  user identity. Read back the named UTC one-shot stop schedule and require the
  configured role, instance target, boolean `Force=true` and `SkipOsShutdown=true`,
  enabled state, no flexible window and an unexpired deadline no more than 24 hours
  away. Print JSON with host, lane, random generation token and deadline. A duplicate
  lane is refused.
- `release <lane> <token>`: release only that exact acquisition. The final release
  requests stop and waits for confirmation while holding the lifecycle lock.
  A stale token or boot generation cannot stop the next holder. Keep the token
  until release succeeds. Failed stops retain the lease for retry.
- `stop`: stop only if the local lease table is empty. There is no force override
  for another lane's lease.
- `status`: show actual EC2 `instance_type`, state and lane names, without printing
  lease tokens.

Tokens are local coordination handles, not AWS credentials. The state file
retains them so a coordinator can recover from a lost terminal. Leases do not
expire automatically: a lost heartbeat must not silently evict a live job.
A completed stop followed by a new native start invalidates old leases when
`LaunchTime` changes. Acquire refuses pending, stopping and stopped instances;
it never waits for stopping and then restarts one itself. Waiting for confirmed
stop before any native restart remains the coordinator's responsibility.

Stop polling is bounded to 300 seconds for the graceful attempt and another
300 seconds after a forced fallback. AWS request timeouts can add to that time.
The forced fallback rechecks for `stopping` under the same lock, then requests
`--force --skip-os-shutdown`; the guest filesystem may need repair. Any unexpected
state, identity/read error or unconfirmed stop fails closed with leases retained.
The independent deadline is left untouched on every path.

## Scope and follow-ups

This lock serializes cooperating processes on one host, not arbitrary AWS
operators or another laptop. The coordinator must not start or otherwise mutate
the instance concurrently with helper operations. Native lifecycle capability
validation remains separate; Scheduler readback does not prove execution-role
trust, stop permission or eventual delivery, and is not a hard real-time stop.

## Detached jobs

- `run <lane> <ship-dir> -- <argv...>`: acquire, checkpoint the exact token locally,
  ship regular files with SCP, submit a detached job, poll and retrieve results.
  Commands execute directly as argv, not interpolated into a remote shell.
- `job-status <lane> <token>`: query that job without releasing its lease.
- `cancel <lane> <token>`: request cancellation of that exact job. This does not
  release the lease; the running collector or a later `resume` must confirm
  terminal status and retrieve the results first.
- `resume <lane> <token>`: reconnect to the checkpointed job, retry an unconfirmed
  submission idempotently, then collect results and release the exact token.
  Preparation failures can be retried while the original ship directory exists.

Job checkpoints are under `$G16_T4_STATE_DIR/jobs` (or the default state directory).
The runner prints the token and resume command before transfer. Three consecutive
poll/retrieval failures return nonzero with the lease and independent deadline
intact. An interrupt also leaves the lease intact. Manual `release` refuses an
unconfirmed managed job, even if its SSH connection has disappeared.

Successful retrieval preserves `terminal.json`, `job.log`, `supervisor.log` and
regular files under `work/out` in the local `results/<token>` directory, along
with the compressed result archive. Both successful and failed commands retain
results. Only then does the collector release the lease and return the command's
exit status. Cancellation returns 130, deadline expiry 124 and supervisor errors
125. A failed instance stop remains an error with the lease retained for retry.

The guest supervisor uses `Popen(start_new_session=True)`, redirected standard
streams and closed SSH descriptors, following the Python
[subprocess documentation](https://docs.python.org/3/library/subprocess.html#subprocess.Popen).
One guest `flock` at the resolved job root's `gpu.lock` covers actual execution,
not merely the local lease. Waiting and running jobs use an absolute execution
deadline 30 seconds before the independently armed stop. Cancellation/deadline
cleanup signals the workload session, including extra groups created by
`timeout`, and waits for executing session members to disappear before recording
terminal status. The workload also inherits the GPU lock descriptor.

A persisted started marker prevents automatic reexecution after supervisor loss.
Without terminal evidence this can leave a job unresolved until the independent
stop. It is safer than running the batch twice or releasing a potentially live
job. Commands must remain in the workload session: privileged commands or jobs
that daemonize with their own `setsid()` are not supported. This is not a cgroup
sandbox, a cross-host lease service or a guarantee against guest/kernel failure.
An `active` status means terminal evidence is absent, not proven liveness.

## Guest bootstrap requirements

Provisioning remains separate. Before any run, provide:

- Python 3, Bash, working SSH/SCP, writable home/job storage and synchronized UTC
  clocks. No package installation, start or launch is performed by this runner.
- A persistent boot/idle watchdog and hard system stop independent of the laptop.
  If `/var/lib/g16-watchdog/lease` exists, queued/running supervisors refresh it
  every 30 seconds; it must be writable by the SSH user. Missing watchdog setup is
  not created or verified by the helper. The hard stop must not be extended by
  heartbeats. Boot provisioning must reset stale watchdog state.
- `G16_T4_SSH_KEY` on the host, or the default
  `$HOME/.ssh/${G16_AWS_KEY:-g16-cuda-bench}.pem`. SSH user defaults to `ubuntu`,
  optionally `G16_T4_SSH_USER`. Batch mode refuses interactive authentication;
  host keys use `StrictHostKeyChecking=accept-new`.
- One shared guest job root for every cooperating lane. It is fixed at
  `~/.cache/snarkrs/t4-jobs`; there is no host remote-root environment setting.
  To use instance-store storage, provision that path as a symlink to a writable
  `/opt/dlami/nvme/g16/t4-jobs` before any job exists. Do not change the symlink or
  delete the root/lock while jobs exist. Instance-store jobs/results do not
  survive an EC2 stop, so retrieve before stopping. Do not mix the old helper's
  different GPU lock with this runner.
- For `cuda-gate.sh`, a trusted `~/g16-env.sh`, sourced with Bash `set -euo pipefail`.
  Set and export `CUDA_HOME` to the installed driver-compatible CUDA toolkit,
  prepend `$CUDA_HOME/bin` to `PATH`, and prepend the real toolkit library
  directory (usually `$CUDA_HOME/lib64`) to `LD_LIBRARY_PATH`, preserving any
  existing value with `${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}`. The loader must find
  `libnvrtc.so`, matching `libnvrtc-builtins.so` and the real driver `libcuda.so.1`.
  Never include the toolkit `stubs` directory. `CUDA_HOME` alone does not configure
  the dynamic loader. Driver/toolkit compatibility and T4 availability still
  require guest validation.

`cuda-gate.sh` now delegates exact-token cleanup to `run`; it has no lane-only
release trap. It sources the guest environment and leaves oracle logic unchanged.
Per-session billing reports and live validation of SSH survival, GPU behavior,
watchdogs and Scheduler delivery remain follow-ups. Host tests establish none of
those production properties.

No AWS, SSH, installation or GPU experiment is needed for the tests:

```sh
bash -n bench/aws/t4.sh bench/aws/cuda-gate.sh
python3 -m unittest discover -s bench/scripts -p 'test_t4*.py' -v
python3 -m unittest discover -s bench/scripts -p test_cuda_gate.py -v
python3 -m unittest discover -s bench/scripts -p test_aws_stop_deadline.py -v
```

The tests inject every AWS response. The cross-process test holds a real local
`fcntl` lock across a simulated waiter timeout and forced stop, while another
process attempts acquisition. Other cases cover stale releases, boot changes,
stop errors, deadline mismatch/expiry, IAM/Owner mismatch and corrupted state.
Durable-job tests run real local detached processes behind fake SSH/EC2, including
lost acknowledgements, reconnect, retrieval failures, cancellation across process
groups, GPU-lock serialization and deadline expiry. CUDA gate tests use host mocks.

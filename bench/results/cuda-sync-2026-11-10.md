# Blocking sync for the CUDA context on a T4 host, 2026-11-10

Lane B of CUDA lane round 3: does `CU_CTX_SCHED_BLOCKING_SYNC` on the CUDA context hand the
core a waiting proof spins on to other work, at what latency cost, and should it be the
default. Main `98eb883` (before lane Z's value-id gather) plus
`G16_CUDA_SYNC=spin|yield|blocking` (unset keeps the driver's default, here `auto`, which
spins while the process has fewer contexts than cores).

One g4dn.2xlarge (8 vCPU = 4 cores x 2 threads, Xeon 8259CL, Tesla T4, driver 595.112.07),
one session, binary zigbuilt with `+adx,+bmi2`. Runner `bench/aws/sync-ab-guest.sh`, tables
`bench/aws/sync-ab-report.py`; co-scheduling with lane X's `bench/aws/coschedule-guest.sh`,
one plan a mode, the modes alternated each round. Every proof verified.

## Summary

- **Blocking frees the core for about 1% of latency.** Host CPU per proof drops from 1.00 to
  1.08 cores to 0.11 to 0.26 (variable work) and 0.04 to 0.05 (constant work); warm
  latency moves +0.0 to +1.6% on variable work, -0.3 to +0.7% on constant work.
- **Yield changes nothing**: same latency as `auto`, still 1.00 to 1.08 cores. It yields
  and spins again, which the kernel still counts as busy.
- **The freed core barely turns into throughput.** Beside a 7-thread CPU stream (lane X's
  `g1c7`), blocking makes the CPU stream 3 to 12% faster and the GPU stream 0 to 2% slower:
  total proofs a second move -1.4 to +0.4% on variable work and +1.3 to +2.7% on constant
  work.
- **On a saturated host blocking hurts.** With the CPU stream on all 8 threads (`g1c8`), the
  blocked GPU thread waits for a core on every wake-up: the GPU stream is 5 to 13% slower on
  variable work and the total drops 4 to 10%. Spinning keeps its core and is not hit.
- **Decision: keep the knob, keep spinning as the default.** The pass bar (<= 2% latency,
  cores well under 1) holds for a single stream, but the core it frees is worth at most
  2.7% of throughput in the best measured layout and costs up to 10% when the host is busy,
  which is the shape of a prover service that solves witnesses on the CPU while the GPU
  proves. `G16_CUDA_SYNC=blocking` is the choice for a host that runs a GPU proof and
  wants the core back for unrelated, non-saturating work.

- On variable work the GPU stream is most of the total (about 60 of 70 proofs a second on
  sha256), so a 3 to 12% faster CPU stream cannot pay for even a 1% slower GPU stream.
  Constant work is the opposite case and gains 1 to 3% in `g1c7`.
- Spinning beside 8 CPU threads costs the CPU stream little (8 threads under spin prove within
  1 to 4% of 7 threads under blocking): the spinning thread and the CPU threads share the host by
  time slices, and the GPU thread is already on a core when its work finishes.
- With blocking, one more CPU thread than free cores is the trap. A deployment that wants
  the core back sizes its CPU work to n - 1 threads, at which point blocking and spinning
  give about the same throughput.

## The device gate under blocking

`bench/aws/cuda-gate.sh` passed on main `52dbb2f` plus the knob both ways, same box, warm
caches: spinning (the committed default) and with blocking forced as the default in a
throwaway build. Every test passed in both, but under blocking `adversarial_gpu` took 222 s
against 80 s and `pipeline_gpu` 17.1 s against 2.4 s. Libtest runs those tests on parallel
threads beside CPU-backend comparisons, which saturates the host: the `g1c8` case again,
at a larger scale because a test makes many short device round trips.

## New leads

- The wake-up cost under a saturated host would shrink if the GPU thread ran at a higher
  priority (nice or `SCHED_FIFO` for the waiting thread); not tried, and it is a deployment
  setting rather than a prover change.
- Cutting the host waits a proof makes (5 to 8 today) would shrink both the blocking cost
  and the gap lane X's two-process runs fill.

# x86 adx+bmi2 A/B: generic vs release flags vs ark-ff asm, 2026-10-10

Binaries from fe8a182 (the Rust source of daf6571, which only adds the A/B runner), built with
`cargo zigbuild --release --target x86_64-unknown-linux-gnu -p snarkrs --no-default-features
--features cpu`, three ways: **generic** (no target flags, the release build before this
change), **adx** (`-C target-feature=+adx,+bmi2`, what `make release-build` now sets for x86_64)
and **asm** (adx plus `--cfg feature="asm"` on ark-bn254 alone via `bench/aws/rustc-bn254-asm.sh`,
experimental). rapidsnark 81eddf1 static build, warm wrapper, once per host. Runner `bench/aws/matrix.py
run --guest ab`, one disposable EC2 instance per type (us-east-1, Ubuntu 22.04), hosts run one at
a time. Each host: 3 rounds, each round every circuit under all three builds back to back with
the build order reversed every round (ABC, CBA, ABC), warm, 10 reps, all logical CPUs (rapidsnark's
ffiasm pool matched the vCPU count). Medians pool the 30 reps per build. Every rep self-verified
(810 per host); one proof per build per circuit plus rapidsnark's first and last passed snarkjs
0.7.6 locally with public signals equal to the reference: 45/45 per host, 135/135 in all.

## Findings

- **`+adx,+bmi2` does not turn on ark-ff's assembly multiply for BN254.** ark-bn254 0.5 derives
  `MontConfig`, and the derive overrides `mul_assign`/`square_in_place` with a copy of ark-ff's
  `cfg(all(feature = "asm", target_feature = "bmi2", target_feature = "adx", ...))`, evaluated in
  ark-bn254, which has no `asm` feature. The adx build has 0 adcx/adox instructions (60.8k mulx,
  all from LLVM) and matches a `+bmi2`-only build's instruction mix apart from the startup guard.
  The asm build has 14.8k adcx/adox. So the release flags buy LLVM's mulx codegen, nothing more.
- Even so, the flags are a win on every host and circuit: m5zn (Cascade Lake) -10.5% to -12.4%,
  c7i (Sapphire Rapids) -1.9% to -10.3%, c6a (Zen 3) -1.4% to -12.5%. Medians across the 9 circuits:
  -11.0%, -6.9%, -3.5%.
- The real assembly adds little on top: median across circuits -12.3% (m5zn), -7.5% (c7i), -3.7%
  (c6a) vs generic, so 0.2 to 1.4 points beyond the flags. It is not uniformly better: on c6a
  sha256, railgun-13x01 and js_16x16_d32, and on c7i railgun-13x01 and js_16x16_d32, asm is slower
  than adx by 0.5 to 3.3 points.
- Where it lands, anon-aadhaar: the NTT moves most (m5zn 2245 to 1938 to 1850 ms, c7i 515 to 466
  to 436 ms, c6a 429 to 419 to 408 ms). With the flags the MSM moves 9% on m5zn, 5% on c7i (whose
  bucket fill is the IFMA radix-2^52 code the flags do not touch) and 2% on c6a.
- Zen 3 gains least from the flags on 7 of 9 circuits (not railgun-01x01 or sha256).
- m5zn.xlarge: the generic build is slower than rapidsnark on js_2x2_d32, railgun-01x01, tornado
  and js_16x16_d32; with the flags it is faster on all nine. The x86 matrix report
  (x86-matrix-2026-10-10.md) already ran the adx build, so its numbers are the "adx" column here.
- Rounds agree: generic is the slowest build in every round of every circuit on every host but
  one (c7i railgun-01x01, round 3). adx vs asm order does flip between rounds on c6a and c7i.

## Caveats

- Three hosts, one instance each; no repeat on a second instance of the same type.
- The asm build needs a rustc wrapper; it is not something `make release-build` can produce today.
- Warm only, all threads only. The startup guard was checked by disassembly (cpuid present, error
  string present) and by the adx and asm builds running on all three hosts; it was not run on a
  CPU without ADX/BMI2.

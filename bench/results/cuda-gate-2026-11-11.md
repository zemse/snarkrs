# Standard CUDA device gate on a T4, 2026-11-11

The standard gate passed on one g4dn.2xlarge (8 vCPU, 32 GiB host RAM, Tesla T4,
15360 MiB driver-reported device memory, driver 595.112.07). The AWS Ubuntu 22.04
image provided CUDA 13.2. Rust binaries were zigbuilt locally at `792eb10` for
`x86_64-unknown-linux-gnu.2.31` with `-C target-feature=+adx,+bmi2`; both CPU features
were checked on the guest. No Rust or Go toolchain was installed remotely.

Runner: `bench/aws/t4.sh` at `51bd444`, with `bench/aws/cuda-gate-guest.sh` and a
locally built static gnark verifier. Go 1.24.0 built the existing gnark v0.14.0
harness offline with readonly modules, `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`.
The guest adapter accepts only the harness's version and proof-verification calls.

- CUDA CLI proofs and verification passed for `tiny_mul` and `sha256`, default
  and constant work, with fallback disabled.
- The one-byte VRAM-limit CLI case correctly fell back to the CPU, verified, and
  did not label the device suspect. This is an intentional fallback test, not a
  CUDA timing.
- The gnark test passed its independent `groth16.Verify` call. The fresh oracle
  receipt was present in retrieved results; a passing Rust process alone is not
  the acceptance condition.
- The gate ended with `GATE PASSED` and terminal exit 0. The extended
  `every_variant_gives_the_same_points` test was not requested. This is the
  standard gate, not every ignored test or production-size coverage.

The warm-up compiled all five kernel units before capped test steps. Its test
process took 949.72 seconds on a fresh guest cache. These runs establish
correctness and gate readiness, not performance comparisons; the timing probes
inside the test suite are not accepted benchmark rows.
